# Архітектура та посібник для розробника

Цей документ — для того, хто буде переписувати, оновлювати, виправляти
або просто розбиратись у коді після мене. Мета: щоб не довелось заново
реверс-інженерити протокол чи вгадувати, чому щось зроблено саме так.

Інші документи в проєкті:
- `README.md` — що це за програма і навіщо вона існує (коротко, для
  користувача).
- `docs/PROTOCOL_NOTES.md` — хронологічний журнал рішень, статусів і
  дрібних "граблів", накопичений під час розробки. Це не структурований
  довідник — радше нотатки "чому це так" з датами. Цей файл
  (`ARCHITECTURE.md`) — структурований довідник "що є що" одноразово, без
  хронології.

Якщо десь тут написане суперечить коду — довіряй коду, онови цей документ.

## Загальна картина

Програма замінює сайт am32.ca/configurator: підключається до
польот-контролера (FC) з прошивкою INAV через звичайний USB-serial порт,
переходить у режим "passthrough" (FC просто ретранслює байти до ESC),
і спілкується з кожним ESC окремо через FourWay-протокол (той самий,
яким користуються BLHeli/AM32-конфігуратори). Читає й пише лише
184-байтний блок налаштувань EEPROM ESC — **не** саму прошивку (`.hex`),
це свідомо поза межами проєкту.

Шари, знизу вгору:

```
┌─────────────────────────────────────────────────────────────┐
│  UI (PyQt6, GUI-потік)                                      │
│  main_window.py, config_editor_widget.py, hotspot_widget.py, │
│  esc_comparison_widget.py, esc_status_widget.py,             │
│  flag_icons.py, theme.py, i18n.py                            │
├─────────────────────────────────────────────────────────────┤
│  Оркестрація (окремий QThread — connection_worker.py)        │
│  esc_manager.py — єдина точка, де приймаються рішення         │
│  "читати/писати/пропустити", і де все логується               │
├─────────────────────────────────────────────────────────────┤
│  Домен (чисті функції/дані, без I/O)                          │
│  eeprom_layout.py, eeprom_fields.py, eeprom_values.py,        │
│  mcu_profiles.py, models.py, eeprom_config.py                │
├─────────────────────────────────────────────────────────────┤
│  Протокол (байти, без бізнес-логіки)                          │
│  msp.py, fourway.py                                           │
├─────────────────────────────────────────────────────────────┤
│  Транспорт                                                    │
│  serial_transport.py (обгортка над pyserial)                  │
└─────────────────────────────────────────────────────────────┘
       + settings_store.py, file_logger.py (наскрізна персистентність)
```

Головне правило цієї архітектури: **кожен шар не знає нічого про шар
вище**. `msp.py`/`fourway.py` не знають, що таке ESC чи налаштування —
лише байти й CRC. `eeprom_*.py` не знають, як дані потрапили в програму
(файл чи ESC) — лише що вони означають. `esc_manager.py` — єдине місце,
де ці шари зустрічаються і приймаються рішення "писати чи ні". UI взагалі
не має прямого доступу до серійного порту — лише через сигнали Qt.

## Як насправді відбувається прошивка — покроково

Це найважливіший розділ, якщо потрібно зрозуміти "як йдуть дані". Простежимо
повний цикл: користувач натискає "Прошити все" в вкладці "Головна" (в
"Хотспот" — той самий шлях, просто автоматично).

### 1. Підключення

```
MainWindow._on_connect_clicked()
  → self.request_connect.emit(port, baud)   [сигнал Qt, черговий міжпотоковий виклик]
  → EscManager.connect(port, baud)           [виконується на worker QThread]
```

Всередині `connect()` (`esc_manager.py`):
1. `SerialTransport(port, baud)` відкриває сам порт (pyserial, `115200` за
   замовчуванням).
2. `_handshake()`: шле `MSP_API_VERSION`. Якщо FC "застряг" у режимі
   FourWay з попередньої сесії (не відповідає на MSP) — явно виходить з
   FourWay (`FourWayClient.exit_interface()`) і чекає 1 секунду, потім
   пробує ще раз. Потім читає `MSP_FC_VARIANT`, `MSP_BATTERY_STATE`,
   `MSP_MOTOR` — суто для технічного логу, на роботу не впливають.
3. `_enter_passthrough()`: шле `MSP_SET_PASSTHROUGH` (команда 245) **з
   порожнім payload** — це і є тригер "легасі" ESC_4WAY passthrough в
   INAV. FC відповідає одним байтом — скільки моторних виходів (ESC) він
   очікує. Потім обов'язкова пауза 2 секунди (`POST_PASSTHROUGH_DELAY_S`)
   — точно як у референсному сайті, ESC-и потребують часу зайти в
   bootloader.
4. Створюється `FourWayClient` на тому самому `SerialTransport` — з цього
   моменту FC вже прозоро ретранслює FourWay-байти до шини ESC.
5. `connection_state_changed(True, expected_count)` — сигнал назад у GUI.

`MainWindow._on_connection_state_changed` при `connected=True` одразу сама
шле `request_discover.emit()` — тобто скан ESC починається автоматично
одразу після підключення, без окремого кліку.

### 2. Сканування (`discover_all`)

Для кожного індексу ESC `0..expected_count-1` викликається `_probe_one(i)`:
1. `FourWayClient.init_flash(i)` — шле `cmd_DeviceInitFlash` (0x37) з
   параметром = індекс ESC. Це і є адресація: bootloader "запам'ятовує",
   який ESC зараз обраний, для всіх наступних Read/Write. У відповідь —
   `signature` (яка мікросхема), `input_pin`, `interface_mode`.
2. `MCU_VARIANTS.get(signature)` — таблиця в `mcu_profiles.py` дає
   `eeprom_offset` для ЦІЄЇ конкретної мікросхеми. **Це обчислюється
   окремо для кожного ESC** — на одному літаку можуть стояти ESC на
   різних мікросхемах.
3. `FourWayClient.read(eeprom_offset, 184)` — шле `cmd_DeviceRead` (0x3A,
   **не** `cmd_DeviceReadEEprom`!) і отримує весь 184-байтний блок
   налаштувань одним запитом.
4. Окремо, best-effort, читається "name block" (32 байти за адресою
   `eeprom_offset - 32`) — звідти береться назва прошивки й тип мотора
   (`parse_name_block` в `eeprom_layout.py`). Якщо це читання впаде —
   не страшно, весь пробінг ESC все одно вважається успішним.
5. `_classify()` порівнює прочитані байти з байтами завантаженого файлу
   конфігу (`self._loaded_config_bytes`) **побайтово** (`==` на `bytes`,
   ніякого "приблизно"): `OK` (збігається), `DIFF` (відрізняється),
   `BLANK` (усі байти `0xFF` або сума `== 0`).
6. `esc_status_changed(i, state, detail, esc_info)` — сигнал у GUI для
   кожного ESC окремо, одразу як він опитаний (не чекаючи всіх 12).

Кожен ESC обгорнутий в `try/except` — якщо один не відповідає
(`ACK_D_GENERAL_ERROR`, бо нічого не підключено до цього виходу), це
ловиться, логується, і скан **продовжується** для решти. Це навмисно:
типовий FC має 12 виходів, а ESC-ів фізично підключено може бути 2-4.

### 3. Прошивка (`flash_bytes`)

```
MainWindow._on_flash_all_clicked()
  → self.request_flash.emit(config_path, None)
  → EscManager.flash_all(config_path, None)
  → load_config_file(path) → flash_bytes(config_bytes, None)
```

(`target_indices=None` означає "визнач сам, що треба прошити" —
`_auto_select_flash_targets()` бере всі успішно опитані ESC і залишає
лише ті, чиї байти **не** збігаються з `config_bytes`; інші одразу
позначаються як `OK` без жодного звернення до заліза.)

Далі для кожного індексу зі списку цілей викликається `_flash_one(i,
config_bytes)` — і ось тут найважливіша гарантія всієї програми:

```python
# _flash_one, спрощено:
info = fourway.init_flash(index)              # 1. заново обрати ESC
mcu = MCU_VARIANTS[info.signature]
current = fourway.read(mcu.eeprom_offset, 184) # 2. СВІЖЕ читання прямо тут
if current == config_bytes:
    return False                               # 3. вже правильно — cmd_DeviceWrite НЕ викликається
fourway.write(mcu.eeprom_offset, config_bytes)  # 4. запис
readback = fourway.read(mcu.eeprom_offset, 184) # 5. обов'язкове контрольне читання
if readback != config_bytes:
    raise VerificationError(...)                # 6. якщо не збіглось — це ПОМИЛКА, не "ніби ОК"
return True
```

Це читання відбувається **прямо перед рішенням писати**, незалежно від
того, що вже вирішив попередній фільтр (`_auto_select_flash_targets`).
Тобто навіть якщо хтось викличе `flash_bytes(..., target_indices=[якийсь
явний список])` в обхід автовибору — усе одно жоден ESC, чий конфіг вже
правильний, не отримає зайвого запису. Це зроблено навмисно на прохання
користувача: **flash-пам'ять ESC не повинна зношуватись даремно**.

Після кожного `_flash_one` — `esc_status_changed` з деталями; після всього
циклу — `flash_finished(success, attempted)` в GUI.

### Хто ще ходить цим самим шляхом

- **Вкладка "Конфіг"** (`config_editor_widget.py`) → кнопка "Записати на
  ESC" → сигнал `apply_requested(bytes)` → `MainWindow._on_apply_from_editor`
  → `request_flash_bytes.emit(bytes, None)` → той самий `flash_bytes`.
- **Вкладка "Хотспот"** (`hotspot_widget.py`) — після кожного успішного
  сканування **безумовно** викликає `flash_bytes` (як і чекбокс "Режим
  автопрошивки" на Головній) — і саме тому, що `_flash_one` сам не пише
  зайвого, це безпечно навіть якщо ESC вже прошитий правильно.

Тобто **весь протокольний код прошивки існує лише в одному місці**
(`esc_manager.py`) — жоден UI-файл не звертається до `FourWayClient`
напряму.

## Модель потоків (threading)

`EscManager` живе на окремому `QThread` (`connection_worker.py`), бо
серійний I/O — блокуючий, а GUI-потік Qt не можна блокувати (інтерфейс
"замерзне").

```python
self.manager = EscManager()
self.manager.moveToThread(self.thread)   # ключовий рядок
self.thread.start()
```

**Як GUI викликає методи EscManager:** НІКОЛИ напряму
(`self.esc_manager.connect(...)` з GUI-коду було б помилкою — виконалось
би на GUI-потоці, а не на worker-потоці, і геть заблокувало б
інтерфейс). Замість цього — через сигнали:

```python
request_connect = pyqtSignal(str, int)          # оголошено в MainWindow
self.request_connect.connect(self.esc_manager.connect)  # підключено у _wire_signals
...
self.request_connect.emit(port, baud)            # виклик — фактично asynchronous
```

Секрет тут — **Qt автоматично робить виклик через чергу подій, якщо
приймач (`self.esc_manager`) живе на іншому потоці, ніж відправник**.
Це визначається за спорідненістю потоку ПРИЙМАЧА (`QObject.thread()`),
а не відправника — тому саме `moveToThread` на самому `EscManager`
(а не на чомусь у MainWindow) і робить усю магію. Якби прямо викликати
`self.esc_manager.connect(...)`, Python виконав би метод одразу на
поточному (GUI) потоці — Qt тут ні до чого, черга спрацьовує лише через
`.emit()`/сигнал-слот.

**Як EscManager повідомляє GUI:** так само сигналами
(`esc_status_changed`, `log_message`, `connection_state_changed`,
`discovery_finished`, `flash_finished`) — вони теж автоматично
переходять на GUI-потік, бо приймачі (`MainWindow`, її методи-хендлери)
живуть там.

**Правило, яке не можна порушувати:** `EscManager` (і все, що він
викликає — `FourWayClient`, `MspClient`, `SerialTransport`) ніколи не
повинен торкатись жодного QWidget напряму. І навпаки — GUI-код ніколи
не повинен викликати методи `EscManager` інакше, ніж через сигнали.
Якщо додаєш нову дію (наприклад, нову кнопку) — спочатку сигнал
`request_щось = pyqtSignal(...)`, підключення в `_wire_signals`, і лише
тоді `.emit(...)`.

## Файл за файлом

### Протокол (без бізнес-логіки, лише байти)

#### `msp.py`
**Навіщо:** реалізація MSP (MultiWii Serial Protocol) v1 — те, чим FC
спілкується з GCS/конфігураторами до входу в passthrough-режим.
**Що робить:** кодування/декодування кадру `$M<len><cmd><payload><crc>`
(v1) і `$X<...>` (v2, для команд з id > 254 — у цій програмі не
використовується, лишено для повноти). CRC для v1 — простий XOR всіх
байтів; для v2 — CRC-8/DVB-S2. `MspClient.send()` — єдина точка входу:
пише кадр, читає відповідь з таймаутом і ретраями.
**Байтовий формат звірений з офіційним пакетом `@am32/serial-msp`
(codec.js/parser.js/commands.js)** — не вгадувався.
**Остерігатись:** `MSP_SET_PASSTHROUGH` (245) **обов'язково** з порожнім
payload — з непорожнім payload INAV очікує інший (тут не підтримуваний)
режим адресації.

#### `fourway.py`
**Навіщо:** FourWay Interface — протокол, яким AM32/BLHeli-конфігуратори
спілкуються з bootloader-ом самого ESC (через FC-passthrough як
"труба").
**Що робить:** кадри `0x2F ... crc` (host→ESC) / `0x2E ... ack crc`
(ESC→host), CRC-16/XMODEM (поліном 0x1021, init 0) над усім кадром
окрім останніх 2 байтів CRC. `FourWayClient.send()` має вбудовані
ретраї (за замовчуванням 10 спроб, 0.2-0.3с таймаут кожна) — і на
таймаут, і на ACK-помилку.
**Остерігатись:**
- Запис/читання конфігу йде через `cmd_DeviceRead`/`cmd_DeviceWrite`
  (0x3A/0x3B), **НЕ** через `cmd_DeviceReadEEprom`/`cmd_DeviceWriteEEprom`
  (0x3D/0x3E) — останні виглядають "правильнішими" за назвою, але
  AM32-bootloader їх для конфігу не реалізує. Це найлегша помилка,
  якщо переписувати код "по назві", а не по джерелу.
- ACK `0x0F` (`ACK_D_GENERAL_ERROR`) — це **нормальна, очікувана**
  відповідь "тут нічого не підключено", а не збій програми. Не варто
  логувати це як щось критичне чи зупиняти скан через неї.
- Сигнатура MCU в `cmd_DeviceInitFlash` — **little-endian на дроті**
  (перевірено проти `four_way.ts`/`flash.ts`).

### Домен (чисті дані/функції, без I/O)

#### `mcu_profiles.py`
**Навіщо:** таблиця "сигнатура мікросхеми → де в її пам'яті лежить
EEPROM-блок налаштувань". Різні ESC можуть стояти на різних
мікросхемах навіть в одному наборі.
**Остерігатись:** `eeprom_offset` завжди обчислюється **окремо для
кожного ESC** з його власної сигнатури (`_probe_one`/`_flash_one` це
роблять правильно) — ніколи не можна закешувати "offset для цього
порту" глобально.

#### `eeprom_layout.py`
**Навіщо:** офсети всіх іменованих полів у 184-байтному блоці + дрібні
декодери (pin, name-block).
**Що робить:** словник `EEPROM_LAYOUT` (ім'я поля → офсет, розмір,
мінімальна версія eeprom), `parse_boot_loader_pin` (закодований байт →
рядок типу `"PB4"`), `parse_name_block` (32-байтний блок → назва
прошивки + тип мотора).
**Джерело:** офсети звірені з `am32-configurator/src/eeprom.ts`,
`parseBootLoaderPin` з `src/mcu.ts` — не вгадувались.
**Остерігатись:** `STARTUP_MELODY` (128 байт RTTTL-мелодія) і
`CAN_SETTINGS` (16 байт) навмисно **не** редагуються ніде в програмі
(немає для них `FieldSpec` в `eeprom_fields.py`) — вони просто
переносяться байт-в-байт разом з рештою блоку. Якщо колись знадобиться
їх редагувати — це окрема, суттєво більша робота (RTTTL — не проста
шкала значень).

#### `eeprom_fields.py`
**Навіщо:** єдине джерело правди для того, як сирий байт перетворюється
на "людське" значення (і назад) — використовується і редактором
(`config_editor_widget.py`), і логом (`eeprom_values.py`), щоб вони
ніколи не могли розійтись у формулах.
**Що робить:** `FieldSpec` (dataclass) на кожне редаговане поле —
офсет (через `EEPROM_LAYOUT`), тип (`bool`/`enum`/`number`/
`number_or_disabled`), формула `value = raw*factor + offset`,
`rendered = value*only_factor` (лише `TIMING_ADVANCE` має
`only_display_factor != 1`), межі, одиниці, версійні обмеження
(`min_eeprom_version`), умовна видимість (`visible_when` — наприклад
`LOW_VOLTAGE_THRESHOLD` показується лише коли `LOW_VOLTAGE_CUTOFF < 2`).
`decode_field`/`encode_field` — перетворення в обидва боки, з
округленням і обрізанням до `[0, 255]` при кодуванні назад.
**Джерело формул:** `am32-configurator/pages/configurator.vue` +
`components/SettingField.vue`.
**Остерігатись:**
- `TIMING_ADVANCE` і `PWM_FREQUENCY` мають по **два** `FieldSpec` в
  списку `FIELD_SPECS` — один для `eeprom_version < 3`, інший для
  `>= 3` (різні формули/діапазони для того самого офсету). Функція
  `applicable_specs(settings)` сама вибирає правильний варіант за
  байтом `LAYOUT_REVISION` в конкретному блоці — якщо додаєш новий
  версійно-залежний варіант поля, роби так само (два записи + версійні
  межі), а не намагайся впхнути логіку "якщо-то" всередину одного
  `FieldSpec`.
- `step` (крок редагування) навмисно **відсутній** у `FieldSpec` —
  повзунки в редакторі рахують позицію в **сирих байтах** (0-255), а не
  в "показуваних" одиницях, саме щоб уникнути ситуації, коли крок у
  показуваних одиницях не ділиться рівно на реальний крок байта
  (наприклад TIMING_ADVANCE v3+: показуваний крок 1°, а реальний крок
  байта — 0.9375°) — і частина можливих сирих значень стає недосяжною
  через повзунок. Якщо додаєш новий тип контролу — зберігай цей
  принцип: контрол оперує байтом, а формула лише форматує підпис.

#### `eeprom_values.py`
**Навіщо:** тонкий форматер `eeprom_fields.py` для технічного логу
(і будь-якого іншого текстового виводу) — **не** дублює формули.
**Що робить:** `decode_settings(settings) -> list[DecodedValue]` —
список `(мітка, текст)` для кожного застосовного поля.
`format_field_value(spec, settings)` — публічна функція, якою
користується і лог, і `config_editor_widget.py` для підписів під
повзунками (**той самий виклик** в обох місцях — навмисно, щоб текст
у редакторі й у логах не міг розійтися). Два поля мають "нестандартне"
форматування, зашите тут окремо (не через загальні флаги в
`FieldSpec`, бо це суто косметика): `ACTIVE_BRAKE_POWER` (0 → "Off"),
`PWM_FREQUENCY` (при `VARIABLE_PWM_FREQUENCY=1` показує діапазон
"XkHz - YkHz").

#### `eeprom_config.py`
**Навіщо:** завантаження/перевірка `.bin`-файлу конфігу з диска.
**Що робить:** `load_config_file(path) -> bytes` — читає файл,
перевіряє що рівно 184 байти (`ConfigFileError` якщо ні). Блок
трактується як непрозорий (без власної контрольної суми) — записується
назад побайтово, як є.

#### `models.py`
**Навіщо:** спільні прості типи даних між шаром протоколу й GUI.
**Що робить:**
- `EscState` (enum: `idle/probing/ok/diff/blank/error`) — статус одного
  ESC для UI.
- `EscInfo` — розшифрована ідентичність ESC (МК, прошивка, bootloader,
  версія eeprom, reversed/3D-режим) **лише для показу**; поле
  `settings: bytes` тут — те, звідки взялась вся ця розшифровка, і саме
  воно використовується вкладкою "Конфіг" для "Read from ESC".
  **Важливо:** `EscInfo` ніколи не бере участі в рішеннях "писати чи
  ні" — це рішення базується виключно на порівнянні сирих `bytes`.
- `ProbeResult` — результат одного опитування ESC (`ok`, `settings`,
  `esc_info`, `error`).

фіксована висота). Якщо вирішиш це дослідити — почни з бінарного
пошуку через реальний `MainWindow` (не ізольовані відтворення), і не

### Оркестрація

#### `esc_manager.py`
**Навіщо:** єдине місце, де протокол (`msp.py`/`fourway.py`) і домен
(`eeprom_*.py`) зустрічаються і приймаються рішення. Живе на окремому
`QThread` (див. розділ про потоки вище).
**Що робить:** повний опис — див. розділ ["Як насправді відбувається
прошивка"](#як-насправді-відбувається-прошивка--покроково) вище.
Коротко: `connect`/`disconnect` (життєвий цикл з'єднання),
`discover_all` (скан + класифікація), `flash_all`/`flash_bytes`
(запис), приватні `_probe_one`/`_flash_one` (per-ESC робота),
`_classify`/`_auto_select_flash_targets` (рішення "що вважати
відповідним/що прошивати").
**Найважливіші інваріанти (не ламати без дуже вагомої причини):**
1. Кожен ESC-індекс обгорнутий у власний `try/except` в
   `discover_all`/`flash_bytes` — одна несправна ESC ніколи не має
   зупиняти обробку решти.
2. Перевірка "чи вже правильно" в `_flash_one` — **свіже** читання
   прямо перед записом, не покладається на кешовані дані з попереднього
   сканування.
3. Після кожного запису — обов'язкове контрольне читання
   (`readback != config_bytes` → `VerificationError`, це і є помилка
   ESC, а не "ніби пройшло").
4. Кожна дія одночасно йде і в GUI (`log_message`/`esc_status_changed`
   сигнали), і в постійний файл-лог (`self._flog`) — не забувай про
   другий виклик, якщо додаєш нову дію.

#### `connection_worker.py`
**Навіщо:** переносить `EscManager` на окремий `QThread`. Дуже
маленький файл, але критичний — див. розділ про потоки.

### UI (PyQt6, GUI-потік)

#### `main_window.py`
**Навіщо:** головне вікно — верхня панель (порт/бод/підключення/мова),
`QTabWidget` з трьома вкладками, панель логів (завжди видима, поза
вкладками).
**Що робить:** будує UI (`_build_top_bar`/`_build_main_tab`/
`_build_config_tab`/`_build_hotspot_tab`/`_build_log_panel`),
підключає всі сигнали (`_wire_signals` — єдине місце, де
`request_*`-сигнали з'єднуються з методами `EscManager`, а сигнали
`EscManager` — з обробниками тут), пересилає стан у дочірні віджети
(наприклад `esc_status_changed` йде одразу в `_esc_widgets` grid, у
`_comparison_list`, у `config_editor`, і в `hotspot_page` — усі чотири
одночасно).
**Взаємне блокування (mutual exclusion):** оскільки `EscManager` тримає
**єдине** з'єднання одразу для всієї програми, коли вкладка "Хотспот"
"озброєна" (`_hotspot_armed=True`) — верхня панель підключення й кнопки
на вкладках "Головна"/"Конфіг" заблоковані (`_on_hotspot_armed_changed`),
і навпаки. **Якщо додаєш новий "режим", який теж хоче володіти
з'єднанням — обов'язково заведи для нього такий самий прапорець і
взаємне блокування**, інакше два режими почнуть змагатись за один
серійний порт.
**Остерігатись:** `closeEvent` перевіряє незбережені зміни в редакторі
конфігу (`config_editor.has_unsaved_changes()`) і питає
зберегти/відкинути/скасувати **перед** закриттям вікна — не видаляй цю
перевірку, не замінюй на просте закриття.

#### `config_editor_widget.py`
**Навіщо:** вкладка "Конфіг" — перегляд, редагування і порівняння
налаштувань у реальних одиницях.
**Що робить:** будує форму **генерично** з `eeprom_fields.FIELD_SPECS`
(групи `QGroupBox`, колонка чекбоксів + сітка 3 колонки для
enum/number-полів). Тримає `self._working_config: bytearray` — робочий
буфер у пам'яті; нічого не пишеться у файл/залізо, доки явно не
натиснуто "Зберегти"/"Записати на ESC". `_original_config` —
знімок при завантаженні, для `diff_text()` (список змінених полів,
показується перед записом і при виході з незбереженими змінами).
`_ClickToWheelSlider`/`_ClickToWheelComboBox` — захист від випадкового
редагування колесиком миші: колесо працює лише коли контрол у фокусі
(клікнутий), і фокус знімається, коли курсор виходить за межі
контролу.
**Остерігатись:** повзунки рахують у **сирих байтах**
(`raw_min = encode_field(spec, min_display)`, і так само `raw_max`) —
див. пояснення в описі `eeprom_fields.py` вище.

#### `esc_comparison_widget.py`
**Навіщо:** компактна таблиця "# / ESC / статус" — той самий потік
даних (`esc_status_changed`), що й велика сітка карток на "Головній",
просто інше представлення. Використовується і на вкладці "Конфіг", і
на "Хотспот" (по одному екземпляру на кожну).

#### `esc_status_widget.py`
**Навіщо:** одна картка ESC на вкладці "Головна" — індекс, кольорова
крапка, короткий статус, і повна розшифровка (МК/прошивка/bootloader/
reversed/3D) у tooltip при наведенні.

#### `manual_counter_widget.py`
**Навіщо:** маленький перевикористовуваний віджет `ManualCounterWidget`
(поле вводу + кнопки "−"/"+") — ручний, редагований оператором лічильник
"скільки ESC насправді перероблено", показаний поруч із автоматичним
розкладом Прошито/Вже коректно/Помилок на обох вкладках "Хотспот"
(`hotspot_widget.py`, `hotspot_line_widget.py`). Доданий 2026-08-26 за
прямим проханням користувача — реальних сценаріїв на конвеєрі забагато,
щоб код завжди вгадав правильний рахунок (переприпаяний ESC, помилка
оператора, перезапуск програми серед партії), тож потрібне поле, яке
можна свідомо підправити вручну, а не лише довіряти автоматиці.
**Що робить:** тримає `int` у діапазоні `[MIN_VALUE=0, MAX_VALUE=100_000]`
за замовчуванням (константи модуля). `QLineEdit` має `QIntValidator(min,
max)` — блокує мінус і будь-які нецифрові символи ще на етапі введення;
`editingFinished` все одно проганяє введене через `set_value`/
`clamp_counter` для підстраховки (порожній рядок, вставка через буфер
обміну тощо). Кнопки "−"/"+" викликають `set_value(value ± step)`.
Публічне API: `value()`, `set_value(v)`, `increment(delta=1)`, `reset()`,
сигнал `value_changed`. `clamp_counter(value, min_value=MIN_VALUE,
max_value=MAX_VALUE) -> int` — чиста функція без Qt, unit-тести у
`tests/test_manual_counter_widget.py`.
**Хто й коли викликає `increment()`:** обидві вкладки "Хотспот" роблять
це **лише** в момент, коли прошивка ДІЙСНО відбулась успішно — та сама
подія, що інкрементує внутрішній діагностичний `_counter_flashed`
(`hotspot_widget.py:on_flash_finished` — напряму; `hotspot_line_widget.py`
— опосередковано, через `HotspotStationController.counters_changed`, з
відстеженням дельти `flashed`, щоб оновлення "вже коректно"/"помилок"
без реальної прошивки НЕ чіпали цей лічильник). Кнопка "Скинути" на обох
вкладках скидає і діагностичні лічильники, і цей — до 0.
**Узагальнено (2026-09-09):** `__init__` тепер приймає опційні
keyword-only `min_value`/`max_value`/`step` (усі за замовчуванням — старі
константи/`1`, тож обидва виклики без аргументів вище лишаються
поведінково незмінними). Другий, зовсім інший споживач —
`hotspot_line_widget.py`'s поле "Перевіряти кожні:" (керування інтервалом
опитування, `min_value=1000, max_value=10000, step=100`) — саме приклад
"колись знадобиться десь ще", на який і розрахований коментар нижче.
**Остерігатись:** якщо колись знадобиться подібний степер ще десь —
перевикористовуй цей клас, не копіюй логіку клампінгу вручну вдруге.

#### `hotspot_widget.py`
**Навіщо:** вкладка "Хотспот" — режим "постав і забудь" для конвеєрної
прошивки **всіх** ESC, які FC повідомляє (до `MAX_ESC_COUNT=12`), по черзі,
кожне сканування зачіпає всі виходи одразу (див. `docs/PROTOCOL_NOTES.md`
за 2026-08-24 та 2026-08-25 для повного опису задуму й того, чому дизайн
змінився на другий день). Це "звичайний" Хотспот для випадку, коли до FC
одразу підключено кілька ESC.

**Не плутати з другою вкладкою "Хотспот (лінія)"** (`hotspot_line_widget.py`)
— то окремий, повністю незалежний сценарій "один оператор обирає один
конкретний ESC-вихід і постійно перебирає через нього ESC по одному", зі
своєю власною стан-машиною (`hotspot_station.py`). Ці дві вкладки
**навмисно НЕ ділять** ні код стан-машини, ні константи фаз — 2026-08-26
короткочасно існувала версія, де обидві вкладки перевели на "дивись лише
на один ESC", і це виявилось помилкою: користувач хотів саме дві РІЗНІ
поведінки в двох вкладках, а не одну поведінку в двох місцях. Якщо колись
знадобиться змінити одну з них — переконайся спершу, що зміна дійсно
стосується ЛИШЕ цієї вкладки.

**Що робить:** `QTimer` (1с) опитує `list_fc_ports()` на присутність
обраного порту й веде невелику стан-машину:

```
IDLE → [Старт] → WAITING_DEVICE
  → [порт з'явився] → CONNECTING
    → [connection_state_changed(True)] → CHECKING
      → [discovery_finished(found=0)] → ROUND_WARNING
      → [discovery_finished(found>0)] → FLASHING (flash_requested)
        → [flash_finished, success==attempted] → ROUND_DONE
        → [flash_finished, success<attempted] → ROUND_ERROR
  → [вичерпано спроби підключення] → ERROR_CONNECT
ROUND_DONE/ROUND_WARNING/ROUND_ERROR → [порт все ще на місці] →
  автоматично CHECKING знову (наступний тік таймера, без перепідключення)
ROUND_DONE/ROUND_WARNING/ROUND_ERROR/ERROR_CONNECT →
  [порт справді зник] → WAITING_DEVICE
```

Все це — **чиста оркестрація поверх існуючих сигналів `EscManager`**,
жодного нового протокольного коду. Викликає `flash_bytes` **безумовно**
після кожного успішного сканування (як і чекбокс "Режим автопрошивки"
на "Головній") — саме тому, що гарантія "не переписувати вже правильне"
живе всередині `_flash_one`, а не тут, це безпечно.

**Важливо (змінено 2026-08-25):** FC лишається підключеним по USB
**весь час**, поки оператор перебирає ESC — міняються лише сигнальні
дроти окремих ESC, підключені до виходів FC, і **ні MSP, ні FourWay
ніяк не сповіщають про це** (FC сам не знає, що дріт від'єднали).
Тому після кожного раунду (готово/попередження/помилка) `_flash_one`
**не розриває з'єднання** — воно просто чекає наступного тіку таймера
(~1с) і одразу запускає новий `discover_all`, на тому самому з'єднанні.
Повторне сканування ESC, який не змінився — нешкідливе й дешеве (жодного
зношування флеша, `_flash_one` й так нічого не перезапише). Розрив
з'єднання відбувається лише тоді, коли сам порт (USB FC) **справді**
зникає зі списку `list_fc_ports()` — це єдина подія, яку можна побачити
програмно.
**Остерігатись:**
- Не додавай сюди рішення "чи потрібно прошивати" — воно вже є в
  `_auto_select_flash_targets`/`_flash_one`. Дублювання цієї логіки тут
  — джерело майбутніх розбіжностей.
- **Не повертай** логіку "чекати, поки порт зникне, перш ніж почати
  наступний раунд" — це був перший варіант дизайну (2026-08-24), і він
  виявився хибним для реального сценарію використання: FC не
  відключають між ESC, тому порт ніколи "не зникає" між раундами, і
  автоматика просто зависала б назавжди в `ROUND_DONE`. Виправлено
  2026-08-25 після реального тестування користувачем.
- **Не переводь цю вкладку на "дивись лише на один ESC"-дизайн другої
  вкладки** — див. пояснення на початку цього розділу.
- `on_connection_state_changed`/`on_discovery_finished`/
  `on_flash_finished`/`on_esc_status_changed` — усі перевіряють
  `self._armed` **першим рядком** і ігнорують сигнал, якщо вкладка не
  озброєна. Це важливо, бо `EscManager`-сигнали глобальні (розсилаються
  всім підписникам одразу) — без цієї перевірки ручна дія на "Головній"
  почала б рухати стан-машину "Хотспоту".
- `_arm()`/`_update_start_stop_button()` викликають
  `self._port_busy_checker(port)` (інжектований з `MainWindow`) перед тим,
  як озброїтись — знайдено на реальному залізі 2026-08-26: якщо ця вкладка
  й "Хотспот (лінія)" (або ручне підключення) одночасно тримають один і
  той самий COM-порт, це ламає не лише того, хто програв гонку за порт, а
  й того, хто виграв (`cmd_DeviceInitFlash` починає повертати
  `ACK_D_GENERAL_ERROR` навіть для ESC, який щойно нормально читався).
  Деталі в `docs/PROTOCOL_NOTES.md`.

#### `hotspot_station.py`
**Навіщо:** стан-машина для ДРУГОЇ вкладки "Хотспот (лінія)"
(`hotspot_line_widget.py`) — сценарій "постав і забудь, дивись лише на
ОДИН обраний ESC-вихід", витягнута в чистий `QObject` без жодного QWidget,
щоб та вкладка могла мати **власний, приватний** `ConnectionWorker`
(власний `EscManager` + власний потік), незалежно від "Головної"/"Конфіг"/
"Хотспот". **Не використовується `hotspot_widget.py`** — та вкладка має
свою окрему, повністю незалежну копію логіки повного сканування (див.
вище) навмисно, щоб зміни тут ніколи не могли випадково торкнутись її.
**Що робить:** `HotspotStationController` веде стан-машину, що після
підключення до FC постійно "дивиться" лише на ОДИН обраний ESC-вихід
(`EscManager.discover_one`, не повний `discover_all`):

```
IDLE → [Старт] → WAITING_DEVICE → [порт з'явився] → CONNECTING
  → [connected] → WATCHING
WATCHING → [поточний тік: discover_one(slot)] →
  не знайдено            → WATCHING (тихо, без "error" у GUI)
  знайдено, вже правильний → ESC_READY (без запису)
  знайдено, відрізняється  → FLASHING (flash_bytes, target_indices=[slot])
    → [success] → ESC_READY   → [failure] → ESC_ERROR
ESC_READY/ESC_ERROR → [поточний тік: discover_one(slot) знову] →
  той самий ESC ще на місці → лишається на місці (без повторного запису)
  ESC зник → WATCHING ("очікуємо наступний")
[сам порт FC справді зник, з будь-якої підключеної фази] → WAITING_DEVICE
```

**Чому не повний `discover_all()` кожен тік:** оператор фізично підключає
лише ОДИН ESC до ОДНОГО конкретного виходу за раз — решта виходів FC
завжди порожні. `discover_all()` (яким і далі користується
`hotspot_widget.py`, з добрих причин — там справді можуть бути підключені
кілька ESC одразу) пробує **кожен** з до 12 можливих виходів щотіку й для
кожного непідключеного логує рядок рівня **"error"** в GUI-панель
(`esc_manager.py`'s `esc_probe_error`) — для сценарію "лише один
конкретний вихід" це було б ~11 "помилок" щосекунди нескінченно.
`discover_one(index)` (`esc_manager.py`, суто адитивний метод, нічого в
`discover_all` не змінено) — та сама логіка `_probe_one`/`_classify`, але
для ОДНОГО індексу, і "не відповідає" там логується лише у файловий лог
(info), ніколи як "error" у GUI — це нормальний, очікуваний стан між
підключеннями ESC, не аномалія.
Рішення "watching → esc_ready чи flashing" — дві чисті, Qt-незалежні
функції `phase_after_discovery(found, last_state)`/
`phase_after_flash(success, attempted)`, unit-тести в
`tests/test_hotspot_station.py`.
**"Підказка про перепідключення живлення" (додано 2026-08-26):**
`esc_manager.py`'s `discover_all()` вже давно попереджає GUI-панель після
`EMPTY_SCANS_BEFORE_POWER_CYCLE_HINT=2` поспіль порожніх сканувань — відома
(за повідомленнями спільноти) особливість BLHeli/AM32-завантажувачів:
багато невдалих спроб підряд може "заклинити" вхід у завантажувач, доки
ESC не перепідключити по живленню. Це попередження **не було перенесено**
на `discover_one()`/цю вкладку при її створенні — знайдено 2026-08-26 при
розборі реального логу, де оператор годинами тестував порядок підключення
проводів ESC (спочатку сигнальний, потім силові — прошиває; спочатку
силові, потім сигнальний — довго/ніколи не детектить), і жодної підказки
не бачив, хоча одна й та сама пряма причина (не спіймано вікно входу в
завантажувач при power-on ESC) якраз і описана в цьому попередженні.
Поріг тут **навмисно НЕ 2**, а `EMPTY_PROBES_BEFORE_POWER_CYCLE_HINT=20`:
для цієї вкладки "нічого не знайдено" — нормальний стан очікування між
підключеннями ESC (весь сенс `discover_one` — не спамити на це), тож
попередження показується (і ховається на `esc_detail_changed`/успішному
`found`) лише після НЕЗВИЧАЙНО довгої (~20с) без перерви серії невдалих
спроб, і рівно ОДИН раз за серію (`==`, не `>=`) — не повторюється щотіку,
інакше знову з'явився б той самий спам, заради уникнення якого й існує
`discover_one`. `HotspotStationController.power_cycle_hint_changed(bool)`
→ `HotspotLinePage._power_cycle_hint_label` (амбер, під `_detail_label`).
**Налаштовуваний інтервал опитування + гарантія "спокійного" часу після
підключення (додано 2026-09-09):** `POLL_INTERVAL_MS=1000` тепер лише
початкове значення — `poll_interval_ms()`/`set_poll_interval_ms(value)`
(клампінг у `[MIN_POLL_INTERVAL_MS=1000, MAX_POLL_INTERVAL_MS=10_000]`,
крок `POLL_INTERVAL_STEP_MS=100` на UI-стороні) дають оператору керувати
цим наживо, навіть поки вкладка озброєна — за проханням користувача, чиї
ESC мають різний час завантаження (одні готові за ~1с, один потребує ~3с).
`MIN=1000`, а не нижче: той самий таймер задає й темп повторних спроб
підключення, а `EscManager.discover_one()` сам по собі може займати до
~0.9с (2 спроби × ~0.2с тайм-аут + 0.25с затримка) — нижче цієї межі
опитування не пришвидшується, а лише накопичує чергу невиконаних запитів
на робочому потоці. **Виправлення реального багу**, знайдене під час
розбору логу поточного `.exe`-сеансу (2026-09-09, 10:55+): `_poll_timer`
запускається один раз у `start()` і ніколи не скидається, а
`EscManager.connect()` займає змінні ~2.0-2.1с (`POST_PASSTHROUGH_DELAY_S`)
— тож затримка до ПЕРШОЇ перевірки щойно підключеного ESC була не
"стабільно ~1с", а випадковим залишком старого відліку таймера: на
реальному залізі зафіксовано від **0.162с до 1.63с** у 12 підключеннях
поспіль, без жодної кореляції з тим, скільки часу минуло між Стоп і Старт
(найкоротша затримка 0.162с трапилась якраз після НАЙДОВШОЇ паузи в усій
серії — 68.5с). Без фіксу налаштовуваний інтервал не гарантував би
повільному ESC реального часу на "спокійний" запуск — перша перевірка
однаково могла прилетіти майже одразу. Виправлено додаванням
`self._poll_timer.start()` у `_on_connection_state_changed` рівно в
момент переходу `connecting → watching` (один раз за підключення, не
щотіку) — тепер налаштований інтервал це РЕАЛЬНА гарантія, а не випадковість.
**Остерігатись:**
- `hotspot_widget.py` (перша вкладка "Хотспот") має ту саму архітектуру
  таймера й, ймовірно, той самий прихований дефект — навмисно НЕ
  виправлено там цією зміною (користувач просив саме цю, "на 1 порт",
  вкладку; див. `docs/PROTOCOL_NOTES.md`). Якщо колись знадобиться —
  переносити фікс окремо, узгодивши з користувачем.
- `HotspotStationController` тримає **власний**
  приватний `EscManager` на власному потоці — методи цього `EscManager`
  викликаються ЛИШЕ через приватні сигнали контролера
  (`_connect_requested`, `_discover_one_requested`, `_flash_requested`, ...),
  ніколи напряму, з тієї ж причини, що й у `main_window.py` (виклик напряму
  виконався б на неправильному потоці). `shutdown()` **обов'язково**
  викликається при закритті програми — інакше потік і серійне з'єднання
  лишаться висіти.

#### `hotspot_line_widget.py`
**Навіщо:** ДРУГА, повністю незалежна вкладка "Хотспот (лінія)" — навмисно
ІНШИЙ сценарій, ніж "Хотспот" (`hotspot_widget.py`): не "прошити всі ESC,
які FC бачить", а "постав і забудь, дивись лише на ОДИН заздалегідь
обраний ESC-вихід" (один список портів, один список ESC-виходів
("ESC 1".."ESC 12"), одна кнопка Старт/Стоп, один пікер конфігу). Існує
тому, що користувач попросив саме ОКРЕМУ ДРУГУ вкладку з ЦИМ іншим
сценарієм, а не зміну поведінки першої (див. `docs/PROTOCOL_NOTES.md` за
2026-08-26 — там же й повна хронологія відкинутих проміжних варіантів,
включно з коротким епізодом, коли обидві вкладки помилково перевели на
цей самий "один ESC"-дизайн).
**Що робить:** `HotspotLinePage` — за формою UI схожа на `HotspotFlashPage`
(той самий загальний layout: пікер конфігу зверху, рядок порту/кнопки
Старт-Стоп, банер, лічильники знизу), але з ESC-виходів-піком замість
таблиці порівняння, і замість сигналів до `MainWindow` (`connect_requested`
тощо) напряму керує своїм власним `HotspotStationController`
(`self.controller`). Порт, ESC-вихід і файл конфігу зберігаються окремо
від усіх інших вкладок (`settings_store.py`: `hotspot_line_port`,
`hotspot_line_esc_index`, `hotspot_line_config_path`) — сенс цієї вкладки
саме в тому, щоб працювати на іншому столі, з іншим виходом і, можливо,
іншим конфігом, ніж перша "Хотспот".
**Навмисно НЕ бере участі** у взаємному блокуванні з "Головною"/"Конфіг"
(`MainWindow._on_hotspot_armed_changed`) — на відміну від
`hotspot_widget.py`. Причина: тут **власний** приватний `EscManager`, тож
немає спільного ресурсу, який треба захищати; ця вкладка й перша "Хотспот"
можуть бути озброєні одночасно на РІЗНИХ портах без конфлікту. На той
самий порт — інша справа: `EscManager.connect()` провалить другу спробу
без падіння програми, але (знайдено на реальному залізі 2026-08-26) це
НЕ просто чиста відмова — постійні повторні спроби підключення однієї
вкладки можуть ламати FourWay-обмін ІНШОЇ, навіть тієї, що "виграла" порт.
Тому `MainWindow` все ж таки інжектує `set_port_busy_checker(...)` сюди
(і симетрично в `hotspot_widget.py`) — не для архітектурного захисту
спільного ресурсу (його тут немає), а конкретно щоб не дати двом
з'єднанням одночасно битись за один і той самий фізичний порт.
**Навмисно НЕ синхронізує** свій пікер конфігу з `MainWindow`/іншими
вкладками (на відміну від `hotspot_widget.py`, яка синхронізує через
`config_path_changed` — там це потрібно для коректності, бо
`_loaded_config_bytes` спільний; тут `HotspotStationController.set_config()`
одним викликом ставить і байти для прошивки, і байти для звірки в СВОЄМУ
приватному `EscManager`, тож той самий клас багу 2026-08-25 тут структурно
неможливий).
**Остерігатись:**
- `_on_start_stop_clicked()`/`_update_start_stop_button()` викликають
  `self._port_busy_checker(port)` перед озброєнням — не видаляй цю
  перевірку, вважаючи, що незалежний `EscManager` робить її зайвою (див.
  абзац вище).
- `MainWindow.closeEvent` викликає `hotspot_line_page.shutdown()` — якщо
  колись з'явиться інший шлях закриття вікна, не забудь про той самий
  виклик, інакше потік і серійне з'єднання лишаться висіти.
- Лейбл шляху до конфігу (`_config_label`) навмисно має
  `setWordWrap(True)` **й** `setMaximumWidth(700)` одночасно — самого
  `setWordWrap` недостатньо: `QLabel.sizeHint()` все одно повертає ширину
  без переносу, поки не заданий явний ліміт, і оскільки всі вкладки
  будуються одразу при старті (не лениво), роздутий `sizeHint` ОДНІЄЇ
  прихованої вкладки роздуває вікно цілком. Той самий фікс зроблено і в
  `hotspot_widget.py` — знайдено 2026-08-26, деталі в
  `docs/PROTOCOL_NOTES.md`.
- Тут НЕМАЄ `EscComparisonList` (на відміну від `hotspot_widget.py`, де
  вона лишається — там дійсно потрібно показувати кілька ESC одразу) — тут
  вона показувала б рядки `0..N-1`, що не мапиться на "один довільний
  watched індекс" без або підробних порожніх рядків над ним, або
  неправильної нумерації. Замість неї — простий `_detail_label`, що просто
  показує текст останнього `esc_detail_changed`.

**Поле "Перевіряти кожні:" (додано 2026-09-09):** рядок під
`_countdown_label` — `ManualCounterWidget` (`min_value=MIN_POLL_INTERVAL_MS,
max_value=MAX_POLL_INTERVAL_MS, step=POLL_INTERVAL_STEP_MS` з
`hotspot_station.py`) + лейбл одиниці "мс" + похідний приглушений лейбл
"(3.0 с)", що оновлюється на кожен `value_changed` (видимий навіть до
озброєння вкладки, на відміну від "Наступна перевірка через..."). Зберігається
окремо від інших налаштувань вкладки (`settings_store.py`:
`hotspot_line_poll_interval_ms`), відновлюється в `_restore_poll_interval()`.
**Навмисно НЕ вимикається** в `_on_armed_changed()` (на відміну від
пікерів порту/ESC-виходу/конфігу вище) — це поле лише міняє
`QTimer.setInterval()` на контролері, без наслідків для стану
протоколу/з'єднання, тож оператор може підняти значення "наживо", поки
вкладка вже спостерігає за повільним ESC, не зупиняючи спостереження.

### Точки входу

#### `main.py`
**Навіщо:** справжня точка входу програми. `QApplication` +
`app.setStyleSheet(QSS)` + `MainWindow().show()` + `app.exec()`.

#### `scripts/run.py`
**Навіщо:** для запуску з вихідного коду без встановлення пакету —
додає `src/` у `sys.path` і викликає `main.py:main()`.
Використовується і напряму (`python scripts/run.py`), і через
`scripts/run_dev.bat`.

#### `scripts/build_exe.py`
**Навіщо:** збирає `dist/EscHotline.exe` через PyInstaller
(`--onefile --windowed`). Прогнати після будь-яких змін коду, щоб
отримати свіжий `.exe`.

`docs/PROTOCOL_NOTES.md`.

#### `scripts/run_dev.bat`
**Навіщо:** зручний запуск з коду без консольного вікна (через
`pythonw.exe` з `.venv`), як альтернатива `.exe`, що не блокується
Smart App Control.

## Найважливіші небезпеки — чого остерегатись

Стисло, все, що вже описано вище, зведене в один список — щоб швидко
перевірити себе перед комітом:

1. **Ніколи не викликай методи `EscManager` напряму з GUI-коду.** Лише
   через `request_*`-сигнали (`main_window.py:_wire_signals`). Пряма
   виклик виконається на неправильному потоці.
2. **Ніколи не чіпай QWidget з коду, що виконується на worker-потоці**
   (`esc_manager.py` і все, що він викликає). Лише сигнали назад.
3. **`cmd_DeviceRead`/`cmd_DeviceWrite` (0x3A/0x3B), не
   `cmd_DeviceReadEEprom`/`cmd_DeviceWriteEEprom`** (0x3D/0x3E) — для
   конфігу ESC.
4. **`MSP_SET_PASSTHROUGH` з порожнім payload.**
5. **`eeprom_offset` завжди per-ESC**, з сигнатури саме цього ESC —
   ніколи не кешувати глобально.
6. **Перевірка "вже правильно" перед записом мусить лишатись у
   `_flash_one`** (свіже читання прямо перед рішенням писати), а не
   лише як фільтр на рівні виклику. Якщо колись переносиш цю логіку —
   переноси гарантію, не лише оптимізацію.
7. **Кожен ESC — окремий `try/except`** в циклах discovery/flash. Одна
   несправна ESC не має валити решту батчу.
8. **Обов'язкове контрольне читання після запису** (`readback ==
   config_bytes`), інакше — `VerificationError`, а не мовчазний
   "успіх".
9. **`STARTUP_MELODY`/`CAN_SETTINGS` не редагуються** — навмисно поза
   `FIELD_SPECS`.
10. **Лише англійська й українська** в `i18n.py` — жодних інших мов.
11. **Технічний лог (`file_logger.py`) — завжди англійською**,
    незалежно від мови інтерфейсу.
12. **Взаємне блокування режимів** ("Хотспот" vs ручне підключення) —
    якщо додаєш новий режим роботи з тим самим `EscManager`, заведи
    такий самий прапорець і блокування елементів керування.
13. **`git add` — лише явні шляхи файлів, ніколи `-A`/`.`** — у
    робочій директорії періодично з'являються дивні 0-байтні файли з
    назвами на кшталт ідентифікаторів коду (ймовірно, побічний ефект
    іншого інструменту/IDE, що теж працює в цій же теці) — перевіряй
    `git status` і прибирай їх перед комітом.
14. **Ніколи не редагуй `~/.esc_hotline/settings.ini` вручну** —
    формат екранування `QSettings` не той, що здається інтуїтивним;
    прав лише через `settings_store.save_last_config_path`.
15. **Хотспот-поллінг (`_on_poll_tick` в обох вкладках) мусить чекати,
    поки попередня спроба `connect_requested` не розв'яжеться, перш ніж
    слати нову** (прапорець `_connect_in_flight`) — `EscManager.connect()`
    містить обов'язкову затримку `POST_PASSTHROUGH_DELAY_S=2.0с`, довшу за
    `POLL_INTERVAL_MS=1000мс`. Без цього прапорця кожне підключення
    гарантовано породжує зайвий, чергу-заблокований `connect()`, який
    провалюється з "Access is denied" одразу після успіху першого — і, як
    підтверджено на реальному залізі, ця невдала спроба відкрити вже
    відкритий порт може зіпсувати FourWay-обмін ПЕРШОГО, успішного
    з'єднання, а не просто мовчки провалитись. Деталі в
    `docs/PROTOCOL_NOTES.md` за 2026-08-26.

## Типові завдання з підтримки

### Додати нове поле налаштувань у редактор

1. Переконайся, що офсет уже є в `EEPROM_LAYOUT` (`eeprom_layout.py`) —
   якщо ні, додай (звіряючись з `am32-configurator/src/eeprom.ts`).
2. Додай `FieldSpec` у `FIELD_SPECS` в `eeprom_fields.py`: офсет (через
   `key`), тип (`bool`/`enum`/`number`/`number_or_disabled`), формулу,
   межі, одиниці, версійні обмеження якщо є.
3. Додай ключ мітки поля (`field_щось`) в `i18n.py`, обидві мови.
4. Додай ключ мітки в `_LOG_LABELS` в `eeprom_values.py` (англійською,
   для технічного логу).
5. **Нічого не треба чіпати в `config_editor_widget.py`** — форма
   будується генерично з `FIELD_SPECS`.
6. Додай тест округлення в `tests/test_eeprom_fields.py` (за зразком
   існуючих — round-trip по всіх 256 значеннях байта).

### Додати нову мову інтерфейсу

**Явно заборонено користувачем** для російської. Для будь-якої іншої
мови — теоретично додати новий код у список `LANGUAGES` в `i18n.py` і
переклад для кожного ключа в `_TRANSLATIONS`, плюс іконку прапорця у
`flag_icons.py`. Але спершу уточни в користувача — це свідоме рішення
проєкту, не техобмеження.

### Додати нову вкладку

Дивись `hotspot_widget.py` як приклад — власний QWidget з власними
сигналами запиту (`щось_requested`), підключеними в
`main_window.py:_wire_signals` до `request_*`-сигналів. Якщо новій
вкладці теж потрібне з'єднання — заведи взаємне блокування (див. пункт
12 вище).

## Крива розгону/спаду (`ramp_curve.py`, `ramp_chart_widget.py`, `motor_test_manager.py`)

- `RampCurve` — кускова кубічна крива Безьє в нормалізованих координатах (x — частка часу, y — частка ходу) для
  розгону й спаду окремо. Для кожної внутрішньої точки збережено **тип ручок** (`modes`): `SMOOTH` — ручки на одній
  прямій (180°), `INDEPENDENT` — кожна ручка рухається окремо (різкий злам, «полиця», керування однією ручкою).
  Тип змінюється правим кліком по точці на графіку; зберігається разом із кривою (JSON `v:2`, `p` — точки, `m` —
  типи; `v:1` читається як «усі гладкі»; зіпсоване/небезпечне -> крива за замовчуванням).
- Інваріанти: x монотонний (крива — функція часу), усі y в [0,1], ручки в межах свого сегмента.
- Мотор не рахує криву на кожному тику: менеджер один раз на відрізок будує таблицю значень по тиках
  (`build_leg_table`, кеш за ключем режим/тривалість/початок/ціль/крок/крива), а тик лише бере значення за часом від
  початку відрізка. Значення, що йде на мотор, обмежене швидкістю зміни `MAX_SLEW_PER_S` (2000 од. MSP/с), щоб
  запізнілий тік не давав стрибка. Стоп/зміна режиму посеред відрізка будує таблицю від поточного значення.
- Маркер на графіку бере час від менеджера (`leg_progress`), тому не розходиться з кривою.

### Графік рампи: точність, синхронність, перевірка (доповнення)
- **Спільні налаштування двох вкладок** («Прогон моторів» і «Прошивка FC»): тривалості (до 0,01 с), межі (дробові відсотки до
  0,01), режим, режим «по черзі», крок оновлення, крива з типами ручок. Зберігаються в одних ключах `settings_store`
  (межі й тривалості — `save_float`/`load_float`, **не** `int`; раніше межі округлялись, а станція читала секунди як цілі).
  Живу синхронізацію дають сигнали `ramp_settings_changed`, `curves_changed`, `chart_view_changed` (див. `main_window.py`).
- **Одна таблиця для мотора й графіка:** `ramp_chart_math.leg_table_msp()` — єдина функція, що дає сире значення MSP на
  кожен тік. Її викликають і `MotorTestManager._solve_leg()`, і графік (`RampChartWidget._table_points()`, `recalculate()`).
  Мотор не може розійтись із тим, що показано. Крок MSP = 0,1 % газу — межа протоколу `MSP_SET_MOTOR`.
- **Кнопка «Розрахувати графік»** (обидві вкладки): розраховує обидва відрізки наново, перевіряє кінці, діапазон і
  найбільший крок за тік, попереджає, якщо крок більший за захист `MAX_SLEW_PER_S`; у «Прогоні моторів» також скидає кеш
  таблиць менеджера (`MotorTestManager.recalculate()`).
- **Галочка «Точки таблиці»** (ключ `motor_test_show_points`): малює на графіку точки таблиці з кроком оновлення.

### Телеметрія ESC (кастомна прошивка INAV 7.1.1 + AM32 ID2BIT)
Джерело: `docs-local/INAV_AM32_ID2BIT_V4_Developer_Guide.docx`. Усе необов'язкове: на звичайному INAV програма просто
пише в журнал «недоступна» і працює як раніше.
- **Виявлення:** при підключенні `MotorTestManager.connect()` викликає `esc_telemetry.probe()` — запит MSPv2 `0x2F00`
  (порожній). Відповідь розбирається `parse_telemetry()` (заголовок 18 байт + 26 байт на ESC, little-endian, версія 1).
  Помилка/тайм-аут/`$X!` = немає прошивки. Результат — рядок у журналі й сигнал `esc_telemetry_available`.
- **MSPv2-відповіді:** `msp._read_msp_response` тепер читає й `$X>`/`$X!` (CRC8 DVB-S2 над flag..payload).
- **Опитування:** `EscTelemetryPoller` (потік менеджера) кожні 30 мс під час прогону (розгін/утримання/спад або повзунок)
  і наживо, якщо увімкнена галочка на вкладці «Телеметрія ESC». Сам вимикається, коли прогін скінчився. 5 збоїв поспіль —
  вимикає опитування, але прогін моторів не зупиняє.
- **Запис:** CSV `<logs>/telemetry/telemetry_YYYYMMDD_HHMMSS.csv` (останні 30), рядок на ESC на опитування: фаза, план за
  кривою (`planned_msp`), відправлене після захисту швидкості (`sent_msp`), їх різниця, RPM, eRPM, RPM на % газу, В, А, °C,
  мАг, `frames`, `new_sample` (лічильник кадрів змінився), `age`, `dt_us`. У технічний журнал — компактний рядок раз на
  секунду та підсумок прогону (макс. RPM, макс. розбіжність план/відправлено, застарілі зразки, приріст CRC-помилок).
- **Вкладка «Телеметрія ESC»:** таблиця живих значень, лічильники парсера, відкриття теки з CSV; живиться підключенням
  вкладки «Прогон мотором» (власного порту не відкриває).
- **Не перевірено на залізі:** розбір і запис покриті тестами (`tests/test_esc_telemetry.py`) на синтетичних кадрах за
  документом; реальний стенд ще потрібен (особливо навантаження на USB: MSP_SET_MOTOR кожні 50 мс + 0x2F00 кожні 30 мс).
- **Телеметрія з обох вкладок:** вкладка «Телеметрія ESC» живиться і від «Прогон мотором», і від «Прошивка FC»
  (`FcFlashStationController.motor_manager`); CSV і журнал пишуться в обох випадках.
- **Відставання:** у підсумку прогону `estimate_lag_ms()` оцінює, на скільки мс крива RPM іде позаду відправленого газу
  (зсув, при якому нормовані криві збігаються найкраще, до 1,5 с), і час відповіді на запит `0x2F00`.

### Прошивка ESC (код AM32 з `.hex`) через FourWay
Модуль `esc_firmware.py`, метод `EscManager.flash_firmware()`, панель `esc_firmware_widget.py` на вкладці «Головна».
Протокол звірено з `am32-configurator` (`flash.ts`, `four_way.ts`, `mcu.ts`), не вгадано.
- **Файл:** `parse_hex()` перевіряє контрольну суму кожного запису і вимагає EOF; `build_image()` будує образ від
  `flash_offset` (прогалини 0xFF); `load_firmware()` відхиляє файл, що сягає `eeprom_offset` (затер би налаштування).
- **Запис одного ESC:** `DeviceInitFlash` → прочитати блок налаштувань → `BOOT_BYTE=0` → `DeviceWrite` по 256 байт від
  `firmware_start` (завантажувач стирає сторінки сам, окремого `DevicePageErase` немає; хвіст добивається 0xFF до 8) →
  зчитування назад і порівняння → `BOOT_BYTE=1`. Збій на будь-якому кроці лишає `BOOT_BYTE=0`: ESC залишається в
  завантажувачі й прошивається повторно.
- **Куди прошивати:** `McuVariant.firmware_start` задано для STM32F051 (`0x1F06`) і ARM64K (`0x3506`, сюди ж потрапляє G071);
  NXP (`0x1506`) не підтримується. Прошиваються лише обрані галочками ESC.
- **Сумісність:** `compatibility()` порівнює назву плати з файлу (32 байти перед блоком налаштувань) з назвою в ESC:
  та сама — ✅; інша назва — ⚠ (потрібна галочка «Дозволити іншу плату»); інший MCU (G071/F051…) — ⛔ блок.
- **Не перевірено на залізі.**
