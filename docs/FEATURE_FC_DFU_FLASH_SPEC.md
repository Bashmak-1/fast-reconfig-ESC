# ТЗ: авто-прошивка FC (DFU) + авто-перехід на прошивку ESC

Цей документ описує фічу незалежно від конкретної реалізації — так, щоб
її міг повторити інший розробник в іншій програмі/мові, маючи лише цей
текст. Він не прив'язаний до назв класів чи файлів поточного проєкту
(EscHotline); там, де згадується конкретний інструмент чи протокол —
це зовнішня, замінна залежність, а не частина самого ТЗ.

## 1. Проблема

Дрон має два пристрої, які треба прошити по черзі:
1. **Flight controller (FC)** — основна плата керування польотом
   (на базі STM32). Прошивається через USB DFU-режим.
2. **ESC (electronic speed controller)** — контролер мотора, до 12 штук
   на одному дроні. Прошивається через FC, який у "прозорому" режимі
   (passthrough) ретранслює команди на ESC по протоколу FourWay/MSP.

Сьогодні це два окремі ручні кроки з двома різними інструментами:
оператор сам стежить, коли FC перейшов у DFU-режим, сам тисне кнопки в
окремій програмі (ST-овому `STM32CubeProgrammer`/`STM32_Programmer_CLI.exe`),
сам перевіряє результат, сам перезавантажує плату, і лише тоді відкриває
другу програму для прошивки ESC.

**Мета фічі:** один екран/вкладка, яка робить увесь цей ланцюжок сама,
без ручного перемикання між інструментами.

## 2. Що саме має статися (happy path)

Оператор заздалегідь обирає:
- файл прошивки FC (`.hex` або `.bin`);
- файл налаштувань ESC (бінарний конфіг, той самий формат, що вже
  використовує існуюча прошивка ESC в цій програмі);
- які саме ESC-слоти прошивати — один або декілька конкретних номерів,
  вибраних явно (не весь діапазон автоматично). Типовий кейс: плата з
  двома ESC на одному фізичному корпусі ("2-в-1"), яка показується FC як
  два окремі виходи — тоді обираються обидва одразу (наприклад, ESC 1 і
  ESC 2), і обидва прошиваються в межах одного автоматичного циклу;
- порт — можна або покластися на автовизначення (нижче), або обрати
  вручну зі списку вже видимих портів той, що вже має звичайну (не DFU)
  прошивку FC — у такому разі програма одразу переходить до підключення
  по FourWay й до прошивки ESC, повністю минаючи очікування DFU.

Натискає "Старт". Далі без участі оператора:

1. **Очікування.** Програма циклічно перевіряє (polling, раз на ~1с), що
   зараз підключено: (a) звичайний FC-порт, (b) FC у DFU-режимі, чи
   (c) нічого.
2. **DFU знайдено → прошивка.** Запускається запис файлу прошивки FC
   через зовнішній інструмент.
3. **Обов'язкова верифікація.** Інструмент запускається з прапорцем
   верифікації (write + verify), і успіх визначається **і** по exit
   code, **і** по явному підтвердженню в виводі інструмента (рядок на
   кшталт "verified successfully") — одного exit code 0 недостатньо,
   бо помилка може бути надрукована, а код повернення — нульовий.
4. **Якщо верифікація не пройшла** → показати помилку оператору,
   **не чіпати плату далі** (не ресетити), дати кнопку "Повторити".
5. **Якщо верифікація пройшла** → послати команду ресету/виходу з DFU
   через той самий зовнішній інструмент.
6. **Очікування нормального режиму.** Програма далі поллить, чекаючи,
   поки плата знову з'явиться як звичайний FC-порт (тобто DFU вже
   немає, FourWay знову можливий). **Важливо:** номер COM-порту після
   цього циклу НЕ гарантовано лишається тим самим — див. 4.5 нижче.
7. **Авто-перехід на ESC.** Щойно звичайний порт з'явився — програма
   **автоматично**, без нового натискання кнопки, підключається до FC і
   починає стежити за заздалегідь обраними ESC-слотами (одним або
   декількома, постійний опит "хто з них зараз видно"), і щойно бачить
   якийсь із них — прошиває туди файл налаштувань ESC тим самим шляхом,
   яким ESC прошиваються в цій програмі й без цієї фічі (FourWay
   passthrough через FC). Слоти, що вже відповідають і вже мають
   коректний конфіг, не чекають на решту — кожен прошивається, щойно
   стає видно, що він того потребує; "повністю готово" настає лише коли
   **всі** обрані слоти знайдені і вже мають правильний конфіг.
8. Показати фінальний стан (успіх/помилка), лічильники спроб.

Якщо DFU взагалі не з'явився, а FC одразу видно як звичайний порт —
кроки 2–6 пропускаються, і програма одразу йде на крок 7 (стеження за
ESC). Тобто прошивка FC — опціональна частина послідовності, не
обов'язкова: фіча однаково корисна оператору, який хоче прошити лише
ESC, не чіпаючи FC.

## 3. Стан-машина (явний список станів)

```
idle
  → waiting_device        (чекаємо: DFU? звичайний порт? нічого?)
    → flashing_fc          (DFU знайдено, йде запис)
      → resetting_fc        (запис підтверджено, шлемо ресет)
        → waiting_fc_normal  (чекаємо, поки з'явиться звичайний порт)
          → connecting        (поєднуємось з FC по FourWay)
            → watching          (стежимо за обраним ESC-слотом)
              → esc_ready | esc_error
      → fc_flash_error      (запис НЕ підтверджено — ручний retry, ресету не було)
    → connecting            (DFU не було, одразу звичайний порт — минаємо прошивку FC)
  → error_connect          (звичайний порт є, але підключитись по FourWay не вдалось)
```

Кожен перехід стану — подія, яку варто писати в лог одним рядком
("stage X → stage Y"), бо під час реального налагодження єдиний спосіб
зрозуміти, що пішло не так, — це послідовність станів і сирий вивід
зовнішнього інструменту.

## 4. Технічні деталі, важливі для реалізації

### 4.1. Як відрізнити DFU від звичайного порту

STM32 USB DFU bootloader — це **не** послідовний (COM) порт. Він
з'являється в системі як окремий USB-пристрій з фіксованим
VID:PID `0483:DF11` ("STM Device in DFU Mode" в Windows Device
Manager). Звичайні засоби виявлення послідовних портів (наприклад,
`pyserial` в Python чи будь-який еквівалент в іншій мові) його **не
побачать** — потрібен окремий механізм виявлення, специфічний для
інструмента прошивки (у випадку ST — прапорець `-l`, що показує список
підключених ST-Link/USB-DFU інтерфейсів).

### 4.2. Зовнішній інструмент, а не власний USB-стек

Прошивку й виявлення DFU варто робити, викликаючи вже існуючий
офіційний CLI-інструмент виробника чипа (в даному проєкті —
`STM32_Programmer_CLI.exe` від STMicroelectronics), а не писати власну
реалізацію USB DFU-протоколу. Причини:
- це той самий інструмент, яким оператор і так користується вручну —
  нуль нового навчання, нуль нової поведінки "про всяк випадок";
- не додає нової залежності на низькорівневу USB-бібліотеку
  (на кшталт `libusb`/`pyusb`);
- виробник чипа вже коректно обробляє всі едж-кейси конкретного чипа.

Інтеграція — звичайний виклик зовнішнього процесу (`subprocess`/
`Process`/еквівалент), з перехопленням stdout/stderr і exit code, із
таймаутом (прошивка не повинна вмер повиснути назавжди — типові
орієнтири: ~10с на список пристроїв, ~120с на сам запис, ~10с на
ресет).

### 4.3. "Ніколи не вір мовчки"

Той самий принцип, що вже діє для прошивки ESC в цій програмі:
- запис FC вважається успішним лише при **явному** підтвердженні
  (і exit code, і текстовий маркер успіху/верифікації в виводі);
- ресет FC у нормальний режим виконується **лише** після підтвердженого
  успіху прошивки — ніколи заздалегідь і ніколи "на удачу";
- якщо інструмент не знайдено на диску (не встановлений / не той шлях)
  — показати зрозумілу помилку оператору, не падати з необробленим
  винятком.

### 4.4. Перехід на ESC — повторне використання наявного шляху

Коли FC знову став звичайним портом — підключення до нього й прошивка
ESC повинні йти **точно тим самим кодовим шляхом**, яким це вже
відбувається в програмі без цієї фічі (той самий протокол,
той самий формат конфіг-файлу). Не винаходити паралельну реалізацію —
лише новий "вхід" в існуючий потік, з автоматичним стартом замість
ручного натискання.

### 4.5. Номер COM-порту FC НЕ стабільний після DFU-циклу

**Підтверджено на практиці** (той самий ефект спостерігався роками на
сайті am32.ca під час ручної прошивки тим самим DFU-кроком): після
прошивки через DFU і перезавантаження FC Windows часто видає **інший**
номер COM-порту, а не той, що був до цього. Номер може просто зрости на
одиницю щоразу (спостерігалось зростання аж за COM400+ після багатьох
циклів) — покладатись на конкретне число не можна взагалі.

**Як це обробляти:** замість того, щоб чекати появи того самого
(заздалегідь обраного) порту, потрібно:
1. Зробити "зліпок" (snapshot) усіх портів, видимих прямо перед тим, як
   починається прошивка FC через DFU (поки система ще бачить попередній
   стан, навіть якщо FC вже зник із цього списку, перейшовши в DFU).
2. Після підтвердженого ресету — на кожному тику поллінгу знову
   опитувати список портів і шукати ті, яких **не було** у зліпку.
3. Якщо з'явився рівно один новий порт — вважати це FC, автоматично
   перейти на нього (оновити "активний" порт у внутрішньому стані) і
   одразу підключатись по FourWay. Жодного ручного втручання оператора
   не потрібно.
4. Якщо з'явилось декілька нових портів одночасно (рідкісний, але
   можливий збіг, наприклад інший пристрій підключили в той самий
   момент) — обрати той, що відповідає відомим USB VID флайт-контролерів
   (та сама евристика, що вже використовується для підсвічування
   ймовірного FC-порту в списку), і залогувати цю неоднозначність.
5. Якщо жодного нового порту ще немає — просто продовжити очікування
   (це нормальний стан "ще не встигло з'явитись").

Це навмисно НІКОЛИ не порівнює номери портів напряму (`new > old` чи
подібне) — тільки "з'явилось нове, чого не було". Такий підхід коректно
працює незалежно від того, чи номер справді змінився цього разу, чи
випадково лишився тим самим.

### 4.6. Стеження за декількома ESC-слотами одночасно

На відміну від класичного "один слот — одне стеження", ця фіча має
вміти стежити за **довільним набором** заздалегідь обраних слотів
одночасно (не лише одним, і не обов'язково всіма підряд):
- кожен тик поллінгу опитується **лише** набір обраних слотів — ніколи
  весь діапазон (це б означало постійні "помилкові" опити для всіх
  інших, непідключених виходів, що засмічує лог/інтерфейс);
- слот, який цього тику не відповів, вважається "поки не підключений"
  — це нормальний очікуваний стан, не помилка;
- якщо кілька обраних слотів одночасно потребують запису — запис
  бажано робити одним пакетним викликом на всі ці слоти разом, а не
  по одному (швидше, і узгоджено з лічильниками успіх/помилка на
  кожен слот окремо, а не на весь пакет);
- інтерфейс показує стан кожного обраного слоту окремо (а не один
  узагальнений рядок), щоб оператор бачив, який саме слот ще не готовий.

### 4.7. Взаємне блокування з іншими функціями програми

Якщо в програмі вже є інші функції, що тримають порт зайнятим
(наприклад, інший тест чи інша вкладка, яка вже підключена до того ж
порту) — нова фіча повинна:
- бачити, що порт зайнятий, і не намагатись підключитись одночасно;
- і сама позначати порт зайнятим на час своєї роботи, щоб інші функції
  програми це бачили.

### 4.8. Налаштування, які варто запам'ятовувати між запусками

- шлях до файлу прошивки FC;
- шлях до файлу налаштувань ESC;
- обраний порт (якщо явний вибір, а не лише автовизначення) — і це
  значення треба перезаписувати автоматично, щойно 4.5 виявив новий
  номер порту після DFU-циклу, щоб наступний ручний старт одразу
  використовував актуальний порт, а не застарілий;
- обрані ESC-слоти (список, не один номер);
- шлях до зовнішнього CLI-інструмента, якщо він не в стандартній теці
  інсталяції (override).

## 5. Що свідомо залишається ПОЗА межами цієї фічі

- Зміна протоколу (наприклад, Dshot300 тощо) на FC як частина цього ж
  потоку — **не включати**. Зміна протоколу зазвичай сама по собі
  вимагає перезавантаження плати; стакати два непідтверджені цикли
  "записав → перезавантажив" (прошивка FC + зміна протоколу) в одній
  непротестованій автоматизації — ризиковано. Якщо потрібно — окрема,
  наступна ітерація, вже на основі реального досвіду з цією фічею.
- Власна реалізація USB DFU-протоколу замість зовнішнього CLI.

## 6. Критерії приймання

- [ ] Програма сама відрізняє "нічого не підключено" / "звичайний FC
      порт" / "FC у DFU-режимі" без дій оператора.
- [ ] При DFU — прошивка стартує автоматично, без додаткового кліку.
- [ ] Ресет FC відбувається **тільки** після підтвердженої (exit code +
      текстовий маркер) успішної верифікації запису.
- [ ] Якщо верифікація провалилась — ресету не було, показано помилку,
      є кнопка ручного повтору.
- [ ] Після повернення FC в нормальний режим — стеження й прошивка
      обраних ESC-слотів стартує **автоматично**, без нового кліку.
- [ ] Можна обрати декілька ESC-слотів одночасно (не лише один) —
      кожен слот стежиться й прошивається незалежно, пакетним записом
      там, де кілька слотів потребують запису в один і той самий момент.
- [ ] Можна обрати порт вручну зі списку вже видимих: якщо обраний порт
      вже має звичайну (не DFU) прошивку FC — DFU-крок пропускається,
      і програма одразу переходить до стеження за ESC.
- [ ] Якщо після DFU-прошивки й ресету FC з'являється під **іншим**
      номером COM-порту, ніж до цього (підтверджений реальний випадок,
      не гіпотетичний) — програма сама це виявляє (за принципом "який
      порт новий відносно зліпка перед прошивкою", не за конкретним
      номером) і автоматично продовжує роботу на новому порту, без
      втручання оператора й без зависання в очікуванні порту, що вже
      ніколи не з'явиться під старим номером.
- [ ] Якщо DFU не з'являвся, а FC одразу в нормальному режимі — прошивка
      ESC однаково працює (прошивка FC — необов'язковий попередній
      крок).
- [ ] Відсутність зовнішнього CLI-інструмента на диску не викликає
      крах — лише зрозуміле повідомлення оператору.
- [ ] Кожен перехід стану і кожен виклик зовнішнього інструмента (повна
      команда, повний stdout/stderr, exit code) логуються в постійний
      файл логу — це єдиний спосіб розібрати, що сталось, якщо оператор
      надішле лог після реального прогону.
- [ ] Нова функція коректно блокує/перевіряє зайнятість порту відносно
      решти програми.

## 7. Відомий незакритий момент (на час написання ТЗ)

Точний текст, який реальний `STM32_Programmer_CLI.exe` друкує у
відповідь на список пристроїв (`-l`) і на успішний запис+верифікацію
(`-w ... -v`), **не був перевірений наживо** на момент першої
реалізації (інструмент не стояв на машині розробника). Перший реальний
