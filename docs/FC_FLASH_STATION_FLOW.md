# Прошивка FC: як влаштований весь конвеєр (FC → ESC → протокол → тест мотора)

Технічний опис того, що саме відбувається на вкладці "Прошивка FC" від
натискання "Старт" до "Готово!" — крок за кроком, з посиланнями на код і
реальні MSP/DFU-команди, що йдуть по дроту. Призначення: щоб за півроку
можна було відкрити цей файл і одразу зрозуміти логіку, не перечитуючи
весь `fc_flash_station.py` заново.

Головний файл-оркестратор: `src/esc_hotline/fc_flash_station.py`
(`FcFlashStationController`). Він координує чотири незалежні під-системи,
кожна на власному `QThread`, щоб жодна довга блокуюча операція (виклик
зовнішнього `.exe`, серійний I/O) не заморожувала GUI:

| Під-система | Файл | Що робить |
|---|---|---|
| `_DfuWorkerThread` | `dfu_flash_manager.py` | DFU-прошивка FC через `STM32_Programmer_CLI.exe` |
| `ConnectionWorker` / `EscManager` | `esc_manager.py`, `fourway.py` | Прошивка ESC через FourWay/bootloader-passthrough |
| `_ProtocolWorkerThread` | вбудований у `fc_flash_station.py` (`_ProtocolWorker`) | Запис протоколу мотора (MSP) |
| `_MotorTestWorkerThread` | `motor_test_manager.py` (`MotorTestManager`) | Фінальний тест-прогін моторів |

## Загальна схема фаз (`self._phase`)

```
idle
 └─ start() ──► waiting_device ──(DFU знайдено)──► flashing_fc ──► resetting_fc ──► waiting_fc_normal
 │                  │                                                                      │
 │          (FC вже в нормальному режимі,                                                  │
 │           DFU прошивку вимкнено прапорцем)                                               │
 │                  └──────────────────────────────────────────────────────────────────────┘
 │                                                                                          ▼
 │                                                                                     connecting
 │                                                                                          │
 │                                   ┌──────────────────────────────────────────────────────┤
 │                                   │ (ESC-прошивку вимкнено)                               │ (ввімкнена)
 │                                   ▼                                                       ▼
 │                           writing_protocol ◄───────────────────────────────────────  watching
 │                                   │                                              ▲        │
 │                                   │                                              │        ▼
 │                                   │                                              └── flashing
 │                                   │                                                       │
 │                                   │ (кожен watched ESC підтверджено ОК) ◄─────────────────┘
 │                                   ▼                                                  esc_ready
 │                      waiting_fc_for_motor_test ◄── (тест мотора вимкнено) ──► all_done
 │                                   │
 │                                   ▼
 │                        connecting_motor_test ──► checking_motor_armed ──► running_motor_test
 │                                                                                      │
 │                                                                                      ▼
 └───────────────────────────────────────────────────────────────────────────────── all_done
                                                                                        │
                                                                        (плату вимкнено, settle-delay)
                                                                                        ▼
                                                                          waiting_device / waiting_fc_normal
                                                                            (автоматично, наступна плата)
```

Помилкові фази (`*_error`) зупиняють автоматичний рух і чекають або
ручного "Повторити" (`retry()`), або зникнення плати (щоб почати
спочатку): `fc_flash_error`, `error_connect`, `esc_error`,
`protocol_error`, `motor_test_error`.

Опитування (`QTimer`, `POLL_INTERVAL_MS` = 1000 мс за замовчуванням,
`set_poll_interval_ms()` дозволяє 1000–10000 мс) рухає станову машину в
`_on_poll_tick()` — більшість переходів відбувається саме там, а не
миттєво по event-ам, щоб не спамити зовнішній CLI/серійний порт частіше,
ніж раз на тік.

## Три незалежні перемикачі оператора

`set_flash_fc_enabled()`, `set_flash_esc_enabled()`, `set_motor_test_enabled()`
(відповідають трьом галочкам на вкладці, всі `True` за замовчуванням).
Можна вмикати/вимикати в будь-якій комбінації:

| FC | ESC | Мотор | Що відбувається |
|---|---|---|---|
| ✅ | ✅ | ✅ | Повний цикл: DFU → ESC → протокол → тест |
| ❌ | ✅ | ✅ | `start()` одразу йде в `waiting_fc_normal` — шукає FC, що вже в нормальному режимі (DFU не чіпається) |
| ✅/❌ | ❌ | ✅ | ESC-цикл повністю пропускається, **але протокол мотора все одно записується** — ESC фізично не заармиться/не ініціалізується на хибному протоколі, тож цей крок обов'язковий, навіть якщо прошивка самого ESC цього разу не потрібна |
| ✅/❌ | ❌ | ❌ | Нічого, крім підключення до FC — одразу `all_done` |
| ✅/❌ | ✅ | ❌ | ESC прошивається, протокол пишеться (бо ESC повинен отримати правильний протокол), але сам тест мотора не запускається — `all_done` одразу після запису протоколу |

Детальний код цього рішення — `_on_connection_state_changed()` (рядки
~1050–1063 `fc_flash_station.py`) та `_on_protocol_write_done()` (рядки
~1147–1159).

## Етап 1 — DFU-прошивка FC (`dfu_flash_manager.py`)

Увесь етап — це по черзі три виклики зовнішнього
`STM32_Programmer_CLI.exe` (ST-Link/USB DFU утиліта, встановлюється разом
з STM32CubeProgrammer). Жодного власного USB DFU стеку в коді немає —
`subprocess` + парсинг stdout.

1. **Пошук DFU-пристрою** — `list_devices()`:
   ```
   STM32_Programmer_CLI.exe -l usb
   ```
   Саме `-l usb`, НЕ голий `-l` (той перелічує RS232-порти, а не USB DFU
   — підтверджено на реальному залізі, див. UM2237). У виводі шукається
   токен `usb\d+` (`usb1`, `usb2`, ...) на кожному рядку — цей токен і є
   `port_id`, яким потім адресується пристрій у наступних викликах
   (`-c port=usb1`). Фаза `waiting_device`, опитується раз на тік, поки
   не знайдеться хоч один пристрій АБО (якщо `flash_fc` вимкнено з
   самого початку) одразу пропускається.

2. **Прошивка + верифікація** — `flash_and_verify()`:
   ```
   STM32_Programmer_CLI.exe -c port=usb1 -w <firmware> [0x08000000] -v
   ```
   `0x08000000` (`FLASH_BASE_ADDRESS`) додається тільки для `.bin` (у
   `.hex` адреса вже вшита). Перед запуском — `DFU_SETTLE_DELAY_S` = 0.7с
   паузи (повторний `-l usb` одразу після попереднього може повернути
   "Target device not found" — драйверу потрібен момент звільнити USB-
   хендл). Успіх визначається НЕ кодом виходу, а буквальним рядком
   `"verified successfully"` у виводі. Фаза `flashing_fc`.

   Прогрес-бар парситься наживо (`_run_streaming` + `_stream_reader`):
   CLI друкує один суцільний рядок на бар без `\r`/`\n` між кроками
   (кожен крок "N%" зліплений із наступним через байт-заповнювач), і
   `\n` з'являється тільки на 100%. Тому читання йде побайтово і
   буфер скидається не лише на `\r`/`\n`, а й на кожен символ `%` —
   інакше весь бар прийшов би одним шматком і прогрес показував би
   лише 0/50/100%.

3. **Вихід з DFU** — `reset_to_app()`:
   ```
   STM32_Programmer_CLI.exe -c port=usb1 -g 0x08000000
   ```
   `-g` ("Go"), НЕ `-rst` — `-rst` смикає ніжку NRST, яка через чистий
   USB DFU взагалі не підключена, і команда одразу провалюється.
   `-g <адреса>` — те саме, що робить галочка "Run after programming" у
   самому GUI STM32CubeProgrammer. Після успіху з'єднання з пристроєм
   обривається — це ОЧІКУВАНИЙ результат (прошивка вже побігла, пристрій
   покинув DFU-режим), а не помилка. Фаза `resetting_fc`.

4. **Очікування повернення в нормальний режим** — фаза `waiting_fc_normal`.
   **Важливо:** COM-порт FC після DFU-циклу НЕ гарантовано лишається тим
   самим номером (підтверджено на практиці: Windows видає новий номер
   щоразу, спостерігалось зростання за COM400+ після багатьох циклів).
   Тому прямо перед стартом прошивки знімається знімок усіх видимих
   портів (`_pre_dfu_port_snapshot`), і після цього шукається будь-який
   порт, якого в тому знімку не було (`choose_reenumerated_port()` —
   якщо кандидатів кілька, перевага віддається тому, що позначений
   `likely_fc` за VID/PID). Ця ж фаза паралельно продовжує слухати DFU
   (на випадок, якщо оператор забув затиснути кнопку DFU, помітив це й
   виправив) — тож одна фаза ловить обидва сценарії.

## Етап 2 — Прошивка ESC (FourWay / passthrough, `esc_manager.py` + `fourway.py`)

Щойно FC знайдено в нормальному режимі, контролер підключається плоским
MSP і переходить у режим passthrough:

1. **Handshake** — `MSP_API_VERSION` (якщо FC досі замкнений у
   FourWay-режимі з минулої сесії — `FourWayClient.exit_interface()` і
   повтор), потім `MSP_FC_VARIANT`, `MSP_BATTERY_STATE`, `MSP_MOTOR` —
   усе лише для технічного логу.
2. **Вхід у passthrough** — `MSP_SET_PASSTHROUGH` (команда 245). Відповідь
   містить кількість ESC-виходів, які FC фактично звітує
   (`expected_count`, обмежено `MAX_ESC_COUNT` = 12). Пауза 2с
   (`POST_PASSTHROUGH_DELAY_S`) — той самий `await delay(2000)`, що й у
   референсному BLHeli-конфігураторі.
3. **Стеження** (фаза `watching`) — раз на тік викликається
   `discover_many(esc_indices)` лише для тих індексів, які оператор
   позначив галочками на вкладці (не всі 12 підряд). Для кожного індексу:
   - `cmd_DeviceInitFlash` (FourWay) — якщо ESC не відповідає, це НЕ
     помилка, а нормальний стан "поки не підключено" (тихо, лише в
     технічний лог);
   - визначається сигнатура MCU → `MCU_VARIANTS` (eeprom-офсет, розмір
     шару налаштувань);
   - зчитується блок EEPROM-налаштувань (`cmd_DeviceRead`) і, якщо
     можливо, блок імені прошивки/типу MCU.
4. **Рішення, що робити далі** — чиста функція
   `phase_after_discovery_many(tick_states, indices)`:
   - якщо хоч один watched-індекс відповів і НЕ збігається з
     завантаженим конфігом (`BLANK`/`DIFF`) → фаза `flashing`, пишемо
     тільки ці індекси;
   - якщо відповіли не всі watched-індекси (деякі ще фізично не
     підключені) → лишаємось `watching`;
   - якщо відповіли всі і всі вже збігаються → `esc_ready` і одразу
     автоматичний перехід до запису протоколу (на відміну від
     "Хотспот (лінія)", тут це НЕ стала точка очікування наступної
     заміни плати — це одноразовий крок).
5. **Прошивка** (`_flash_one` в `esc_manager.py`):
   - перед записом — свіже читання поточних налаштувань ще раз
     (захист від гонки, навіть якщо попередній probe це вже робив);
   - якщо вже збігається — запис взагалі пропускається (`cmd_DeviceWrite`
     не викликається — нуль зайвого зношення flash);
   - байти ідентичності/ревізії бутлоадера (`BOOT_LOADER_REVISION` тощо,
     `eeprom_layout.IDENTITY_FIELD_NAMES`) з файлу конфігурації НІКОЛИ не
     записуються як є — вони завжди підміняються актуальними байтами з
     ЦЬОГО ESC (`with_identity_from`), бо це властивості конкретного
     заліза/бутлоадера, а не налаштування, і чужі значення тихо
     відхиляються прошивкою;
   - після запису — обов'язкове контрольне читання (`cmd_DeviceRead`) і
     побайтове звірення з тим, що щойно писали (`VerificationError`, якщо
     не збіглось) — "ніколи не довіряй запису без зчитування назад".

## Етап 3 — Запис протоколу мотора (`_ProtocolWorker` у `fc_flash_station.py`)

Щойно всі watched ESC підтверджено ОК (або якщо прошивку ESC вимкнено,
але тест мотора — ввімкнено), контролер:

1. Виходить з FourWay (`_disconnect_requested` → `EscManager.disconnect()`
   → `FourWayClient.exit_interface()` + закриття порту). Фаза
   `writing_protocol` виставляється ОДРАЗУ, але сам запис чекає
   підтвердженого `connection_state_changed(False)` від ESC-воркера —
   це явна синхронізація, щоб уникнути гонки між закриттям порту одним
   потоком і відкриттям того самого порту іншим (`_ProtocolWorker` живе
   на окремому `QThread`).
2. Відкриває новий plain-MSP зв'язок на тому самому порту і виконує:
   - `MSP_API_VERSION` (із тим самим fallback через
     `FourWayClient.exit_interface()`, якщо FC досі "застряг" у
     FourWay-режимі одразу після виходу);
   - `MSP_ADVANCED_CONFIG` — читає поточні `motor_pwm_rate`/`servo_pwm_rate`
     (байти 4-6 і 6-8 відповіді), щоб відіслати їх назад НЕЗМІННИМИ —
     змінюється тільки сам протокол (байт 3);
   - `MSP_STATUS_EX` — перевірка `ARMED`-біта (`0x04` в `armingFlags`,
     offset 13-15 відповіді); якщо FC заармлений — запис одразу
     скасовується (`protocol_error`);
   - `MSP_SET_ADVANCED_CONFIG` з новим індексом протоколу
     (`motor_ramp.build_advanced_config_payload`);
   - `MSP_EEPROM_WRITE` (таймаут 3с, 3 спроби — підтверджено на реальному
     залізі, що збереження в EEPROM може тривати довше за попередній
     бюджет ~2с);
   - `MSP_REBOOT`.
3. Протокол (`STANDARD`/`ONESHOT125`/`MULTISHOT`/`BRUSHED`/`DSHOT150`/
   `300`/`600`, `motor_ramp.MOTOR_PROTOCOLS`) застосовується лише при
   завантаженні таймер/DMA-драйвера (`pwm_output.c`) — "на льоту" його
   змінити не можна, тому це завжди супроводжується перезавантаженням, і
   з'єднання після цього вважається мертвим.

Якщо тест мотора вимкнено — на цьому все закінчується (`all_done`).
Інакше — фаза `waiting_fc_for_motor_test`.

## Етап 4 — Автоматичний тест мотора (перевикористовує `MotorTestManager`)

Та сама машина, яку сама вкладка "Прогон мотором" використовує для
живого ручного тесту — запущена тут як приватний воркер, із тими самими
налаштуваннями (тривалості розгін/утримання/спад, крива, режим "всі
одночасно"/"по черзі", межі швидкості), які оператор уже налаштував на
вкладці "Прогон мотором" (читаються свіжо з `settings_store` щоразу,
а не кешуються тут окремо).

1. **Очікування перезавантаженого FC** (`waiting_fc_for_motor_test`) —
   той самий трюк зі знімком портів "до", що й після DFU-скидання: нова
   поява під новим чи тим самим іменем ловиться через `_pick_reenumerated_port`.
2. **Підключення** (`connecting_motor_test`) — `MotorTestManager.connect()`:
   plain MSP (без passthrough), читає `MSP_MOTOR` (щоб визначити реальну
   кількість моторів — `count_active_motors`) і `MSP_ADVANCED_CONFIG`
   (щоб показати поточний протокол на вкладці "Прогон мотором", якщо
   відкрита одночасно).
3. **Перевірка disarm** (`checking_motor_armed`) — та сама перевірка
   `MSP_STATUS_EX`/`ARMED`-біта, що й у запису протоколу. Якщо
   заармлений, або FC не звітує жодного мотора — `motor_test_error`.
4. **Сам прогін** (`running_motor_test`) — `start_sweep(up_s, hold_s, down_s)`:
   - цикл на `QTimer` з кроком `TICK_MS` = 100 мс (10 Гц);
   - значення на кожному тіку рахується виключно з часу, що минув від
     початку поточної фази (`PHASE_UP`/`PHASE_HOLD`/`PHASE_DOWN`), ніколи
     накопичувально — немає дрейфу від пропущеного тіку;
   - лінійна інтерполяція або "Безе" (`ramp_chart_math.segment_value`) між
     нижньою (`_min_target`, типово 1000 = 0%) і верхньою (`_max_target`,
     типово 2000 = 100%) межею, в сирих MSP-одиницях (1000–2000);
   - режим "всі одночасно" (`TEST_MODE_ALL`) рухає кожен реальний мотор
     однаково; "по черзі" (`TEST_MODE_SEQUENTIAL`) рухає рівно один
     мотор за раз (решта — на `MSP_MIN`), автоматично переходячи до
     наступного після завершення спаду попереднього, аж доки не
     пройдуть усі;
   - кожен тік надсилається `MSP_SET_MOTOR` (команда 214) — завжди
     рівно 8×uint16 (жорсткий формат прошивки), невикористані слоти —
     завжди `MSP_MIN`;
   - будь-яка клавіша (поки вкладка/вкладка-джерело у фокусі) або кнопка
     "Стоп" — це НЕ аварійний інший шлях, а той самий плавний спад до
     нижньої межі, просто запущений негайно з поточного значення;
   - по завершенню останнього спаду (`PHASE_IDLE`) контролер відключається
     від FC і виставляє фінальну фазу `all_done`.

## Лічильники (`counters_changed`, і три нові per-stage сигнали)

- `fc_flash_succeeded` — рівно один раз за плату, в `_on_reset_fc_done()`,
  одразу після успішного `-g` (вихід з DFU).
- `esc_flash_succeeded` — рівно один раз за плату, або в
  `_on_discovery_finished()` (усі watched-ESC вже збігались без жодного
  запису), або в `_on_flash_finished()` (запис відбувся і
  `success == attempted > 0`).
- `motor_test_succeeded` — рівно один раз за плату, в
  `_on_motor_phase_changed()`, коли фаза повертається в `PHASE_IDLE`
  після прогону.

Кожен сигнал емітується лише з ОДНОГО місця коду — того самого, де
відповідний етап щойно реально завершився успішно. Якщо галочка етапу
вимкнена, цей код просто ніколи не виконується — окрема перевірка
галочки на боці лічильника не потрібна. На віджеті (`fc_flash_widget.py`)
кожен сигнал напряму інкрементує свій власний `ManualCounterWidget`
("FC:", "ESC:", "Мотори:") — лічильники не персистентні, скидаються
на старті нової сесії програми, і додатково вручну кнопкою "Скинути".

Окремо є старі агреговані `counters_changed(flashed, ok, errors)` —
кількість ESC-записів/збігів/помилок по ESC-слотах (не по платах), що
відображаються на вкладці окремим рядком, як і раніше.

## Автоматичний перехід до наступної плати

Фаза `all_done` не зупиняє конвеєр назавжди: `_on_poll_tick()` чекає, поки
поточний порт FC фізично зникне (плату вимкнули/від'єднали), потім ще
`NEXT_BOARD_SETTLE_DELAY_S` = 2с "заспокоєння" (порт може раз моргнути
при вимкненні), і повертається в `waiting_device`
(або `waiting_fc_normal`, якщо DFU-прошивка вимкнена) — готовий до
наступної плати без ручного Стоп/Старт.

## Актуальний порядок (v1.1.3, замінює старі формулювання вище про ранній запис протоколу)

1. DFU-прошивка FC, потім `-g` (запуск). **Жодного зайвого перезапуску/запису протоколу одразу після DFU.**
2. Звичайний режим FC, стеження за ESC (`watching`), прошивка ESC через FourWay.
3. Після ESC-етапу **один повний перезапуск FC із протоколом**: `MSP_SET_ADVANCED_CONFIG` + `MSP_EEPROM_WRITE` +
   `MSP_REBOOT` завжди (у фінальному етапі, навіть якщо протокол уже збігається; за галочкою «Виправляти протокол»).
   Причина: після FourWay виходи моторів лишаються в passthrough-стані, поки FC не перезавантажено, інакше мотори
   пищать як на STANDARD.
4. `waiting_fc_for_motor_test` -> `waiting_motor_init` (пауза, за замовчуванням 3 с, налаштовується степером у вкладці,
   ключ `fc_flash_motor_init_wait_ms`) -> `connecting_motor_test` -> тест. Пауза потрібна, щоб мотори самі завершили
   ініціалізацію й не стрибали на 20-30 %.
5. Сторожові таймери `PHASE_WATCHDOG_S` виводять застряглі перехідні фази у відповідну фазу помилки.
6. DFU-прошивка має до 3 спроб (`FLASH_ATTEMPTS`) для збоїв USB; звичайний «збій запису по USB» показується лише
   після вичерпання спроб.

### Нагадування оператору (`fc_flash_widget.py`)
- Звук Windows «Notify» (галочка «Звук-підказка», `fc_flash_sound_cue`): одразу при `connecting -> watching`, далі
  кожні 30 с у фазах `watching` та `all_done` (після тесту: нагадування «вимкніть живлення», перший раз через 30 с).
  Мовчить на Стоп, помилках, DFU. Таймери перезапускаються **лише при справжній зміні фази** (станція повторно
  надсилає ту саму фазу на кожному опитуванні; без цього відлік постійно зсувався).
- У фазі `watching` через 60 с без живлення з'являється вікно поверх усіх («Увімкніть живлення»), повертається кожні
  60 с, зникає, коли фаза змінилась (ESC знайдено/Стоп).

### Фінальний перезапуск не залежить від вимкнених етапів
Запис протоколу + повний перезапуск FC виконується завжди після всього, що ввімкнено: хоч DFU вимкнено, хоч ESC
вимкнено, хоч тест моторів вимкнено, хоч усе разом. Якщо тест вимкнено, станція після перезапуску чекає на повернення
FC (`waiting_fc_for_motor_test`), потім ту саму паузу на ініціалізацію моторів (`waiting_motor_init`) і лише тоді переходить у `all_done` (так перезавантажену плату не сприймають за нову).
Єдина умова — галочка «Виправляти протокол»: без неї протокол лише перевіряється, без запису й перезапуску.

### Тест моторів вручну (галочка «Тест лише вручну (кнопка)», ключ `fc_flash_motor_test_manual`)
Після всіх увімкнених етапів, фінального перезапуску FC із протоколом і паузи на ініціалізацію станція не запускає тест
сама, а стає у фазу `waiting_motor_start`. Оператор натискає «Старт тесту моторів» тоді, коли йому треба
(`start_motor_test()` -> `connecting_motor_test` -> звичайний тест). Перевірки, чи щось прошивалось, немає. Якщо плату
вимкнули, поки станція чекала на кнопку, вона переходить у `all_done` і йде до наступної. Ця галочка діє незалежно від
«Тест моторів» (автоматичний тест при цьому не запускається).
